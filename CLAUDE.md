# CLAUDE.md — Правила проекта Underwater AI Sensing Platform (UAISP)

Этот файл содержит обязательные правила разработки для данного репозитория.
Claude Code должен следовать им во всех сессиях без напоминаний.

---

## 1. Общие правила разработки

1. **Коммит после каждого этапа** — любое законченное логическое изменение
   (новый метод, модуль, документ) должно быть закоммичено отдельным коммитом
   с описательным сообщением на английском (тело коммита может содержать
   технические детали и ссылки на источники).
2. **Push после каждого коммита** — не накапливать несколько локальных
   коммитов без отправки на удалённый репозиторий.
3. **PEP8** — весь Python-код обязан соответствовать PEP8 (докстринги, тайп-хинты,
   длина строк ≤ 79-99 символов, snake_case для функций/переменных).
4. **Не дублировать репозитории** — работа ведётся в текущем репозитории
   (`Leonidy431/color_sensor`, ветка задачи). Новые репозитории создаются
   только по явному прямому запросу пользователя.
5. **Не симулировать результаты** — если что-то не проверено (push, тесты,
   API-вызов), это не должно описываться как выполненное. Все заявления о
   статусе подтверждаются реальным выводом команд.
6. **Перед выводом "работа потеряна/не сохранилась" — сначала `git fetch`**
   (см. раздел 1.1). Локальный кэш `origin/*` может быть устаревшим, и
   команда `git log origin/branch` без предварительного `fetch` покажет
   состояние на момент клонирования, а не реальное текущее состояние
   удалённой ветки.

### 1.1 Урок: не доверять локальному кэшу origin/* без fetch

В этой сессии был момент, когда `git log --oneline origin/<branch>`
показал только один старый смёрженный коммит, что выглядело как полная
потеря всей проделанной работы (PATENT.md, CLAUDE.md, калибровочный код).
После `git fetch origin <branch>` оказалось, что реальная удалённая ветка
содержит всю историю — просто локальная ссылка `origin/<branch>` не была
обновлена перед проверкой. Работа не терялась.

**Правило:** всегда выполнять `git fetch origin <branch>` перед тем как
делать выводы о том, что сохранилось на удалённом репозитории, и перед
тем как что-либо перезаписывать/пересоздавать "с нуля" из предположения
об утере. Если после `fetch` локальная и удалённая ветка разошлись
(push отклонён с `fetch first`) — не форсировать перезапись, а
разобраться, что именно расходится, и осознанно смёржить/перебазировать.

## 2. Правило научного обоснования алгоритмов

Все алгоритмы обработки сигналов, коррекции и классификации, добавляемые
в проект, обязаны иметь научное обоснование:

1. Искать первоисточники в **PubMed** и **Google Scholar** (или их аналогах
   через WebSearch, если прямой доступ недоступен).
2. Указывать конкретную ссылку/DOI/автора и год в докстринге метода.
3. Если точное численное значение параметра (коэффициент, порог) не может
   быть надёжно взято из литературы для конкретных условий эксплуатации
   (например, локальная мутность воды) — не хардкодить произвольное число.
   Вместо этого:
   - использовать опубликованное значение как значение по умолчанию
     (fallback) с явной пометкой "литературная оценка, требует калибровки";
   - предусмотреть метод эмпирической калибровки по реальным измерениям
     (например, `calibrate_from_samples()`), который заменяет табличное
     значение на измеренное для конкретного места работы.

## 3. Правило выбора решения при неопределённости

При технической неопределённости (нет единственного очевидного решения,
несколько архитектурных или алгоритмических вариантов конкурируют) применяется
следующая эвристика:

> **Правило "299/48/32":** рассмотреть широкий пул кандидатных решений
> (ориентировочно до 299 вариантов/источников/паттернов из литературы,
> практики отрасли и типовых решений), оценить их по представительному
> набору технических критериев (ориентировочно 48 параметров: точность,
> производительность, энергопотребление, устойчивость к шуму, сложность
> реализации, поддерживаемость, стоимость вычислений на edge-устройстве,
> научная обоснованность, воспроизводимость и т.д.), и выбрать вариант,
> получивший наилучшую совокупную оценку с точки зрения разных профильных
> областей экспертизы (ориентировочно 32 профиля: DSP-инженер, специалист
> по машинному зрению, океанограф, ихтиолог, археолог, embedded-инженер,
> специалист по MLOps, специалист по метрологии датчиков и т.д.).

Практическое применение (без буквального перебора 299 вариантов/32 агентов
ради траты ресурсов):

1. Провести реальный обзор литературы/практики (WebSearch/PubMed/Scholar)
   по 2-5 наиболее релевантным альтернативам.
2. Сравнить их по ключевым инженерным критериям, применимым к задаче
   (не обязательно всем 48 сразу — брать релевантное подмножество),
   рассматривая задачу с точки зрения разных профильных областей экспертизы.
3. Явно задокументировать выбор и его обоснование в докстринге/комментарии
   или в отдельном разделе HLD-документа, включая, какие альтернативы были
   отклонены и почему.
4. Не использовать эвристику как повод для избыточной работы — если решение
   очевидно (единственный общепринятый метод, единственный вариант API),
   оценка пула альтернатив не требуется.

## 4. Правила автономной фоновой работы (governance)

Для любых сценариев автономной/циклической работы агента (регулярные
фоновые проходы, cron-циклы, самостоятельные повторные запуски без
присутствия человека) действуют принципы идемпотентности, устойчивого
состояния, контроля контекста, детерминированности, наблюдаемости,
самоисцеления, песочницы, экономии токенов, интеграции инструментов,
асинхронности, управления секретами, критериев остановки и
мета-рефлексии.

Полный перечень (99 директив по 13 категориям, оформленный как
"Симпозиум Перипатетиков") — см. **`AUTONOMOUS_AGENT_GOVERNANCE.md`**.
Этот проект пока работает в интерактивном режиме (без реального
непрерывного фонового контура), поэтому из 99 директив уже сейчас прямо
применимы:

- Состояние проекта — только через `git status`/`git diff`, не через
  память модели (раздел 1.1 этого файла).
- Всегда `git fetch` перед выводом о потерянной/отсутствующей работе.
- Мета-контроль: перед нетривиальным действием — необходимо ли оно, или
  это избыточная работа (overengineering)?

Остальные директивы (sandboxing, распределённые блокировки, event-driven
cron, Circuit Breaker/DLQ) описывают инфраструктуру непрерывного
автономного контура и внедряются только когда появится конкретная задача
для реальной фоновой автономной работы — это прямое применение Правила
"299/48/32" (раздел 3): не строить инфраструктуру без конкретной
потребности.

## 5. High-Level Design (HLD) — 12 фаз проекта

Проект состоит из трёх основных активов (см. `PATENT.md`):
Fish Color Analyzer (AS7262), BlueOS Fish AI Module (Hailo-8L),
BlueOS SBP AI Module (археологическая детекция).

| Фаза | Название | Содержание | Статус |
|------|----------|------------|--------|
| 1 | **Научная валидация базовых алгоритмов** | Проверка и цитирование коэффициентов поглощения воды (Mobley 1994, Pope & Fry 1997, Solonenko & Mobley 2015), модели иридесценции (Gur et al. 2013, Funt et al. 2017); добавлена эмпирическая калибровка `calibrate_absorption()` вместо жёстких констант, проверена регрессией на синтетических данных | ✅ Завершена (`color_fish_analyzer.py`) |
| 2 | **Метрологическая калибровка AS7262** | Калибровка по эталонной мишени методом отношений (Spectralon-стиль), температурная компенсация (кремниевый фотодиод, ~0.6%/°C), коррекция дрейфа по периодическому переизмерению эталона; `calibrate_temperature()`, `calibrate_white_reference()`, `check_drift()` | ✅ Завершена (`color_fish_analyzer.py`) |
| 3 | **Датчик глубины/давления — интеграция** | Драйвер MS5837 (протокол TE Connectivity - PROM/CRC4, компенсация давления 2-го порядка), гидростатический перевод давления в глубину (плотность воды - параметр, не константа), `DepthSyncBridge` со сторож-таймером устаревания показаний для синхронизации с измерениями AS7262 | ✅ Завершена (`depth_sensor.py`), физика/CRC4 протестированы; **компенсация давления НЕ проверена на реальном железе** (нет доступа к физическому датчику в этой сессии) |
| 4 | **Компенсация иридесценции — расширение** | Fresnel-модель тонкой плёнки (формула Эйри) для одного слоя гуанина, предсказание сдвига пика отражения по углу, эмпирическая `calibrate_crystal_thickness()` по многоугловым наблюдениям | ✅ Завершена как **однослойное приближение** (`color_fish_analyzer.py`); полная N-слойная матрица переноса (реальная микроструктура иридофора многослойная, Gur 2013/Funt 2017) — вне текущего объёма, возможное дальнейшее расширение |
| 5 | **Датасет для классификации видов рыб** | Сбор/поиск размеченных датасетов (Fish4Knowledge, QUT Fish Dataset), аннотация цветовых профилей видов | ⛔ Заблокирована: требует реального доступа к внешним датасетам (загрузка, хранение, разметка) — вне возможностей текущей сессии, не код-задача |
| 6 | **Обучение и квантование моделей для Hailo-8L** | YOLOv8n детектор, MobileNetV3 классификатор, экспорт в HEF через Hailo Dataflow Compiler | ⛔ Заблокирована зависимостью от Фазы 5 (нет датасета) и отсутствием GPU-кластера/проприетарного Hailo Dataflow Compiler в этой среде; mock-режим уже реализован в `blueos_fish_ai_module` |
| 7 | **Data Fusion — валидация весов** | Проверка весов visual_weight/color_weight на реальных данных, ROC-анализ, кросс-валидация | ⛔ Заблокирована зависимостью от Фазы 6 (нет обученной модели, нечего валидировать) |
| 8 | **SBP: валидация сегментации грунта** | Реальные данные SUBPRO2545 или синтетика на основе физики акустики (уравнение сонара), сравнение с геологическими кернами | Не начата — следующий кандидат: HLD явно допускает синтетику на физике акустики как альтернативу реальным данным, это можно сделать без внешних ресурсов |
| 9 | **SBP: археологическая датировка — валидация** | Проверка диапазонов глубин по периодам на реальных археологических отчётах (например, данные подводных экспедиций) | ⛔ Заблокирована: нужны реальные архивные/полевые отчёты, которых нет в этой среде; частично можно продвинуть — сверить существующие константы `archaeological_detector.py` с опубликованной литературой по седиментации (не полная замена реальной валидации) |
| 10 | **MAVLink — полевые испытания** | Проверка на реальном автопилоте (ArduSub/BlueOS), задержки, throttling алертов | ⛔ Заблокирована: нужно физическое ROV/автопилот, недоступно в этой среде |
| 11 | **Web UI — интеграция реальных данных** | Замена mock-данных в routes.py на реальные вызовы движков, WebSocket нагрузочное тестирование | Требует ревизии: часть routes.py уже вызывает реальные методы движков (не хардкод), mock — осознанный fallback без Hailo-железа, а не "фальшивые" данные; нагрузочное тестирование WebSocket можно сделать без реального ROV |
| 12 | **Итоговая верификация и документация** | End-to-end тесты, обновление PATENT.md и README, финальный аудит PEP8/типизации | Не начата — имеет смысл только после того, как реализуемые без внешних ресурсов фазы (3, 4, 8, частично 11) завершены |

### Принцип работы по фазам

- Каждая фаза — отдельный набор коммитов с самостоятельным push.
- Перед реализацией фазы, если есть техническая неопределённость,
  применяется Правило "299/48/32" (раздел 3).
- Фаза считается завершённой только когда код проходит существующие тесты
  (`tests/`) и обновлена документация.
- **Честность статуса (CLAUDE.md §1, правило 5):** фаза, требующая
  внешних ресурсов, недоступных в текущей среде (реальное железо,
  внешние датасеты, GPU-кластер, проприетарные тулчейны), помечается
  ⛔ с явным указанием блокера — а не пропускается молча и не
  "закрывается" суррогатной работой, которая создаёт видимость
  прогресса без реальной валидации.

## 6. Структура репозитория

```
color_sensor/
├── CLAUDE.md                        # этот файл — правила проекта
├── AUTONOMOUS_AGENT_GOVERNANCE.md   # 99 директив автономной работы
├── PATENT.md                        # патентная декларация активов
├── README.md                        # документация Fish Color Analyzer
├── color_fish_analyzer.py           # AS7262: спектр → цвет → свежесть →
│                                     # калибровка (Фазы 1-2), иридесценция
│                                     # Fresnel-модель (Фаза 4)
├── depth_sensor.py                  # MS5837: датчик глубины/давления,
│                                     # синхронизация со спектром (Фаза 3)
├── tests/                           # Тесты Фаз 3-4 (корневые модули)
├── blueos_fish_ai_module/           # Hailo-8L: детекция/классификация рыб
│   └── src/{hailo_inference,data_fusion,api,mavlink}.py
├── blueos_sbp_ai_module/            # Hailo-8L: археологическая детекция SBP
│   └── src/{sbp_parser,hailo_sbp_inference,archaeological_detector,api,mavlink}.py
└── blueos_hsi_camera_module/        # NVIDIA Orin: гиперспектральная
    │                                 # классификация материалов (Ecotone UHI)
    └── src/{hsi_calibration,spectral_analysis,api}.py
```

Примечание: `PATENT.md` пока описывает только первые три актива
(Fish Color Analyzer, Fish AI, SBP AI); HSI-модуль — новый актив,
патентную декларацию для него предстоит добавить отдельным этапом.
