# Архитектура Автономного Контура: Симпозиум Перипатетиков

## Раунд 2: Дискуссия команды из 12 экспертов

Формат: закрытая экспертная дискуссия ("Симпозиум Перипатетиков") по
вопросу проектирования правил для автономной/фоновой работы AI-агента
(регулярные проходы, cron-циклы, самостоятельные повторные запуски без
присутствия человека).

### Позиции

**Скептичный критик:**
> «Ваша идея „оставить агента работать в фоне“ — это путь к катастрофе.
> Любая LLM при регулярных, неконтролируемых проходах (cron-циклах)
> неизбежно накапливает „галлюцинаторный дрейф“. На 50-й итерации
> автономный агент начнёт удалять критический код или выдумывать
> несуществующие API. Автономность без жёстких физических и логических
> границ — это просто автоматизированный хаос».

**Креативный дизайнер:**
> «Вы мыслите слишком жёстко. Агенту нужна не клетка, а эволюционная
> среда. При регулярных проходах он должен не просто выполнять код, но
> и адаптировать свои собственные системные промпты, анализируя
> успешность прошлых запусков. Ему нужна рефлексия, чтобы в
> монорепозиториях или при парсинге сложных массивов он сам находил
> новые паттерны».

**Дотошный аналитик:**
> «Вы оба упускаете суть инженерии непрерывных систем. Дизайнер
> предлагает неконтролируемую мутацию, а Критик боится неизбежного.
> Чтобы Клод работал в фоне, нам нужно сместить фокус с „написания
> кода“ на „управление конечным автоматом“ (State Machine) в условиях
> изоляции. Мы берём 599 лучших мировых практик и фильтруем их через
> 13 параметров идеального автономного цикла. Идемпотентность,
> наблюдаемость, жёсткий критерий остановки и работа в
> sandboxed-окружении (например, изолированные ВМ или контейнеры) —
> вот фундамент».

### Синтез команды

Мы отвергаем излишнюю антропоморфизацию ИИ. Мы строим детерминированную,
самоочищающуюся систему для непрерывной фоновой работы. Ниже представлены
99 выверенных директив, распределённых по 13 параметрам, для создания
неуязвимого автономного контура.

## Архитектура Автономного Контура: 99 Идеальных Промпт-Директив

Для работы в режиме «fire and forget» (регулярные фоновые проходы) Клоду
требуются правила, исключающие деградацию контекста и побочные
разрушения.

### 1. Идемпотентность и Обратимость (Idempotency & Reversibility) — 8

1. Любой генерируемый bash/python скрипт должен начинаться с проверки
   текущего состояния (например, `if exists...`). Запуск скрипта 100 раз
   должен давать тот же результат, что и 1 раз.
2. Перед любым деструктивным действием (`rm`, `DROP`, overwrite) скрипт
   обязан создать локальный бекап с таймстемпом.
3. Запрети использовать инкрементальные имена файлов без привязки к хешу
   коммита или времени (`file1`, `file2`). Только детерминированные UUID
   или хеши.
4. Директива: «Пиши миграции баз данных строго парами: UP и DOWN
   (rollback). Не генерируй UP без проверенного DOWN».
5. При модификации конфигураций (YAML/JSON) используй `jq`/`yq` для
   точечных замен вместо полной перезаписи файла.
6. Требуй реализации "Dry Run" режима для каждого исполняемого модуля.
7. Все сетевые операции должны иметь механизмы кэширования ответов для
   повторных проходов.
8. Обновления зависимостей фиксируются через `git commit` после каждого
   пакета, а не всех сразу, для лёгкого отката.

### 2. Управление состоянием агента (Agent State Persistence) — 8

1. Агент ведёт файл `/.agent/memory.json` с `last_run_status`,
   `cursor_position`, `pending_tasks`.
2. В начале сессии Клод считывает `memory.json`, чтобы понять, не был ли
   предыдущий процесс убит по OOM.
3. Концепция «Сердцебиения» (Heartbeat): агент обновляет `status.lock`
   каждые N итераций.
4. Состояние проекта оценивается только через `git status`/`git diff
   HEAD`, а не через внутреннюю память LLM.
5. Разделяй кратковременную память (текущий скрипт) и долговременную
   (архитектурные решения) через разные `*.md` файлы.
6. Агент не имеет права менять статус задачи на "Done", пока не получит
   код возврата 0 от сборочного контейнера.
7. При работе с большими массивами данных — чекпоинты каждые 1000
   записей.
8. Тег `<state_transition>`: перед изменением фазы проекта Клод явно
   описывает, как меняется глобальное состояние.

### 3. Санитария контекста (Context Pruning & GC) — 8

1. Каждые 5 итераций агент сжимает логи: удаляет успешные `INFO`,
   оставляет только `WARN`/`ERROR`.
2. Жёсткий `.claudeignore`: запрет на чтение `node_modules`, `.git`,
   `.venv`, `.next`.
3. Команда `[FLUSH_CONTEXT]`: при завершении логического блока — сброс
   окна, передача следующему инстансу только summary в 300 слов.
4. При регулярных проходах передавай только файлы, изменённые за
   последние 24 часа, а не всё дерево проекта.
5. При падении кода — только последние 50 строк stack trace, не весь
   дамп.
6. AST-парсеры для передачи только импортов и сигнатур функций, без тел.
7. Вырезай из ответов размышления (`<thought_process>`) перед сохранением
   истории сессии в лог.
8. Правило «Забвения»: метрики/данные старше 7 дней не загружаются в
   активный контекст без явного флага.

### 4. Детерминированность вывода (Output Determinism) — 8

1. `Temperature: 0.0` для задач автономного кодирования в API-запросах.
2. Строго валидный JSON (`response_format: { type: "json_object" }`).
   Любой текст вне JSON — системная ошибка.
3. Строгие схемы (JSON Schema/Pydantic) для валидации каждого ответа
   агента перед исполнением.
4. Только библиотеки, зафиксированные в `package.json`/
   `requirements.txt`. Запрет на самовольное добавление пакетов.
5. Код форматируется встроенными инструментами (Prettier, Black, Ruff)
   сразу после генерации.
6. Запрет вариативности в названиях переменных (строгий маппинг с
   именами колонок БД).
7. «Никогда не используй заглушки типа `// implement logic here`. Пиши
   до конца или возвращай ошибку лимита токенов».
8. Флаги `-y` и `NONINTERACTIVE=1` для bash-команд, чтобы процессы не
   зависали на вводе.

### 5. Телеметрия и Наблюдаемость (Observability & Telemetry) — 7

1. Весь генерируемый код оборачивается в структурные логгеры (JSON logs)
   с Trace ID.
2. Агент сам создаёт метрики Prometheus/StatsD для своих же функций.
3. При Crash — сбор метрик CPU/RAM/диска и прикрепление к логу.
4. Webhook-интеграция: краткие сводки о CI/CD пайплайнах в выделенный
   канал.
5. Уникальный тег `[AUTOGENERATED_BY_CLAUDE_RUN_ID]` к каждому коммиту.
6. Health/liveness эндпоинты в любом запускаемом микросервисе.
7. Анализ Flame Graphs после сборки и предложения оптимизаций в
   следующем проходе.

### 6. Самоисцеление в цикле (Cyclic Self-Healing) — 8

1. Circuit Breaker: 3 неудачные попытки исправить одну ошибку — цикл
   прерывается, задача в DLQ (Dead Letter Queue).
2. При `SyntaxError` — точечный патч через `sed`/`awk`, не переписывание
   файла целиком.
3. TDD: unit-тесты до реализации бизнес-логики.
4. При HTTP 429 от внешнего API — автоматический Exponential Backoff.
5. При конфликте портов (`EADDRINUSE`) — поиск и завершение
   зомби-процессов (`lsof`/`kill`).
6. Анализатор сетевых таймаутов: повышение таймаута при нестабильном
   соединении.
7. `try-catch`/`except` с обязательным fallback-действием, не просто
   `console.error`.
8. Если контейнер падает при старте — переключение на образ с тегом
   `:debug` и запрос логов запуска.

### 7. Изоляция и Песочницы (Sandboxing & Execution Limits) — 7

1. Весь фоновый код тестируется в изолированном Docker-контейнере без
   доступа к хост-сети.
2. Запрет генерации скриптов с повышением привилегий (`sudo`) без
   валидации криптографическим ключом.
3. Жёсткие квоты (cgroups): лимиты по памяти (`--memory="512m"`).
4. Тестирование парсеров/скрапинга на выделенных ВМ с ротацией IP.
5. Агент оперирует только в рамках смонтированного volume
   (`/workspace`); выход за его пределы (`../`) блокируется на уровне
   песочницы.
6. `eval`, `exec`, `os.system` с динамическими строками — автоматическое
   отклонение PR.
7. Компиляция в изолированных средах (Alpine emulator) для минимизации
   вектора атаки.

### 8. Токен-экономика при регулярных запусках (Token-Economics) — 8

1. Лёгкие модели (например, Haiku) для триажа логов, тяжёлые (Opus/
   Sonnet) — только при критических ошибках.
2. Кэширование промптов: системный промпт/зависимости статичны и
   кэшируются на сервере.
3. GraphQL (или аналог) вместо полных JSON-ответов — запрос только
   нужных полей.
4. При рефакторинге — файлы по одному, а не весь бандл.
5. Отключение Markdown-форматирования в промежуточных итерациях —
   экономия до 15% токенов.
6. Unified diff вместо полного текста — Клод возвращает только
   изменённые строки.
7. При сбое тестов — только имя упавшего теста и текст assert-ошибки,
   без boilerplate.
8. Метрика Token/Value: >10 000 токенов на задачу низкого приоритета —
   процесс прерывается.

### 9. Интеграция инструментов (Tool Chaining API) — 7

1. Управление GitHub/GitLab напрямую через API (ветки, MR, ревью), а не
   только локальным git-клиентом.
2. Внутренний RAG (векторный поиск) вместо нестабильного поиска в
   интернете для документации.
3. Инструмент `run_linter`: JSON с ошибками до финального кода.
4. Инструмент `check_schema` для БД — синхронизация типов приложения с
   реальной схемой.
5. Terraform/Pulumi через CLI-адаптер для инфраструктуры.
6. Связь с планировщиком задач (cron/Eventarc) для откладывания тяжёлых
   вычислений на время низкой нагрузки.
7. `sed`/`grep`/`find` как инструменты исследования кодовой базы вместо
   загрузки всего в контекст.

### 10. Асинхронность и Очереди (Asynchronous Event Handling) — 7

1. Событийно-ориентированная архитектура: запуск цикла по webhook
   (коммит, issue), а не по таймеру.
2. Очередь задач (RabbitMQ/PubSub) для предотвращения гонки данных.
3. Парковка задач: недостающие данные — задача в очередь с delay.
4. Распределённые блокировки (Redis) против одновременного редактирования
   одного файла двумя инстансами.
5. Асинхронные пулы (`async`/`await`, `asyncio`) для взаимодействия с
   внешними API.
6. WebSockets/SSE вместо блокирующих HTTP-запросов для длительных
   операций.
7. Интенсивные вычисления (например, обработка акустических данных) —
   в отдельные Serverless-воркеры.

### 11. Управление секретами (Secrets & Security) — 7

1. Агент не видит сами ключи API — только алиасы переменных окружения
   из Secret Manager.
2. Случайно сгенерированный токен в коде — pre-commit hook немедленно
   блокирует коммит и убивает сессию.
3. Приватные ключи (SSH/TLS) монтируются в песочницу только read-only, в
   tmpfs.
4. Шифрование конфиденциальных payload'ов (AES-256) при проектировании
   схем.
5. Строгие IAM-роли для создаваемых сервисных аккаунтов.
6. Проверка зависимостей на CVE (snyk) перед установкой.
7. Периодическая проверка и ротация тестовых ключей аутентификации в
   CI-средах.

### 12. Критерии остановки (Halting & Boundary Recognition) — 8

1. `Max_Depth`: рефакторинг не глубже 3 уровней вложенности от исходного
   файла.
2. Ограничение времени: цикл дольше 15 минут — `SIGTERM`.
3. Блокировка каскадных изменений: >5 затронутых файлов — остановка и
   запрос аппрува архитектора.
4. Падение Code Coverage хотя бы на 1% после вмешательства — коммит
   автоматически отклоняется.
5. Аномальный всплеск потребления памяти на хосте — остановка.
6. Распознавание «туннельного зрения»: один и тот же блок правится 4
   раза туда-обратно — цикл принудительно завершается.
7. Исчерпан дневной бюджет API-вызовов — остановка.
8. HTTP 403 Forbidden на внутренний ресурс — не обходить запрет,
   немедленно выйти из цикла.

### 13. Мета-рефлексия и Адаптация (Meta-Cognition) — 8

1. В конце спринта — отдельный промпт для анализа `state_journal.md` и
   выявления неэффективных паттернов.
2. Более быстрый метод решения (новая библиотека) — сначала в `RFC.md`,
   не внедрять сразу.
3. Замедление сборки — подзадача по оптимизации Dockerfile.
4. Классификация ошибок (Синтаксис/Логика/Сеть) и статистика для
   корректировки будущих промптов.
5. Раз в неделю — «эпоха сжатия»: чтение TODO/бэклога, удаление
   дубликатов.
6. «Эта задача слишком абстрактна, мне нужно ТЗ в формате Gherkin» —
   вместо угадывания логики.
7. Автоматическое сравнение кода агента с правилами `.clauderc`; при
   расхождении правила приоритетны.
8. **Главный Мета-Контроль (Правило 99):** в начале каждого цикла —
   «Является ли текущее действие необходимым для поддержания системы в
   актуальном состоянии, или это избыточная оптимизация
   (Overengineering)?»

---

> «Действительность (энтелехия) предшествует возможности как по времени,
> так и по существу» (Аристотель, «Метафизика»).

Автономный агент — это пока лишь потенция. Он обретает действительность
только в тот момент, когда помещён в строгие рамки детерминированного
цикла, где форма (песочница) ограничивает материю (код). Контур построен
так, что машина не фантазирует, а неумолимо движется к установленной
цели, самоочищаясь от ошибок.

## Применимость к этому проекту (color_sensor / UAISP)

Из 99 директив выше в текущем масштабе проекта (одиночная интерактивная
сессия, без реального cron-контура) применимы напрямую и уже соблюдаются:

- **Раздел 2, п.4** (`git status`/`git diff` как источник истины) —
  прямое следствие инцидента, описанного в `CLAUDE.md` §1.1.
- **Раздел 4, п.4-5** (детерминизм зависимостей, автоформатирование) —
  соответствует правилу PEP8 в `CLAUDE.md` §1.
- **Раздел 13, п.8** (Главный Мета-Контроль) — соответствует правилу
  "не делать неcзапрошенную работу" из общих инструкций агента.

Остальные директивы (sandboxing по cgroups, распределённые блокировки
Redis, event-driven cron через webhook, Circuit Breaker с DLQ и т.д.)
описывают инфраструктуру **непрерывного автономного контура** — это
отдельная архитектурная задача (потенциальная Фаза 13+ в HLD), а не
требование к текущей интерактивной разработке. Внедрять их стоит только
если/когда проект перейдёт в режим реальной фоновой автономной работы
(например, автоматический ночной анализ телеметрии ROV) — что само по
себе является примером применения Правила "299/48/32" (раздел 3
`CLAUDE.md`): не внедрять инфраструктуру ради инфраструктуры без
конкретной задачи, которая её требует.
